Phase file: supabase/phase43.sql (+ phase43_test.sql). Web: web/customers.js (+ tests/web/customers_test.js). You MAY edit web/pos.js (only the parts for the customer tier chip + tier discount button + gift reminder) and nothing else shared. Regs: docs/regs/customers.md. DB names a43*.

Existing: table customers (mobile unique, name, type retail|wholesale, credit_limit, active), customer_dues(), find_customer RPC, record_sale2 (latest definition: grep `function public.record_sale2` across supabase/phase*.sql and use the LAST one; it takes p_discount_kind 'amount'|'percent'), POS in web/pos.js (customer block near `drawCust`), dues page web/dues.js.
Owner's words: "Customer add option / variant types of customers: walking - Elite - Gold - find out more variants and add to this system. I can offer them variant facilities - gift - discount. Build this in the software."
## What to build
1. **customer_tiers**: id, code (immutable), name_bn/name_en, rank (order), color, badge icon/emoji, is_default (the walk-in tier), discount_percent (the pre-approved POS discount for this tier, 0..100), discount_cap_amount null (max taka per bill), credit_limit_default null, birthday_gift text, perks text (free text shown to staff), points_multiplier (default 1), auto_rules: min_lifetime_spend, min_orders, min_orders_12m, min_months_active (all optional), active. Seed 6 sensible tiers (Walk-in, Regular, Silver, Gold, Elite/VIP, Wholesale/Party, Staff) with the discount and thresholds blank/zero for the owner to fill - nothing invented as policy: seed names only, discounts 0.
2. **customers** gets: tier_id (default tier), tier_locked bool (manual override stops auto-upgrade), birthday date null, anniversary null, address, notes, customer_since, source, whatsapp; `customer_tier_history` (append-only: customer, from_tier, to_tier, reason auto|manual, by, at). Keep existing columns; type retail|wholesale stays for pricing/credit rules.
3. **Loyalty & gifts (all switchable, default OFF)**: `loyalty_rules` rule keys: loyalty_points_on, points_per_100_taka, point_value_taka, redeem_min_points; `customer_points_ledger(customer, delta, reason sale|redeem|adjust|expire, sale_id, at)` append-only, balance function; `gift_rules(id, tier_id null=all, trigger birthday|anniversary|first_purchase|every_n_purchases|spend_threshold|manual, threshold numeric, gift_text_bn/en, value_taka null, active)` and `customer_gifts(id, customer, rule_id, issued_at, valid_until, claimed_at, claimed_sale_id, note)`; function `gifts_due(customer)` listing unclaimed/eligible gifts (birthday within N days, etc.); claiming records who/when (idempotent).
4. **Automatic tier refresh**: `customer_tier_refresh(p_dry boolean default true)` (owner) computes each non-locked customer's tier from lifetime net spend (sales net of returns), order counts and the tier thresholds; DRY RUN returns the list of changes (who moves from what to what) and writes nothing; real run writes history. Switch `customer_tier_auto_on` default OFF. Never downgrades unless rule `customer_tier_allow_downgrade` ON.
5. **POS integration (server)**: when a sale has a customer whose tier has discount_percent > 0 and rule `tier_discount_on` (default OFF) is ON, a percent discount up to that tier percent (and cap) is treated as pre-approved: it must NOT require the manager approval path of `pos_discount_manager` / discount_over_limit for that part, but anything above the tier percent still follows the normal approval rule. Implement by re-creating record_sale2 from its latest definition with the smallest possible change (copy the whole function; diff yours against the original and prove only that block changed; run the existing sale tests that cover it: supabase/phase12_test.sql, phase20_test.sql and tests for discounts). Record `tier_id` and tier discount applied in the sale's note/JSON so reports can show tier usage. Points are earned by a function `loyalty_award(sale)` called from a separate AFTER INSERT trigger on sales (like `sales_packaging_out` in phase19) - never inside record_sale2 - and only when loyalty_points_on.
6. **Web `#/customers`**: customer master list (search by name/mobile, filters by tier / type / has due / birthday this month / inactive via the collapsed controls), tier chips with color, add customer (quick form: mobile, name, tier, birthday, address, notes) with duplicate-mobile handling, edit, ⋮ menu (change tier + reason, issue gift, adjust points, open dues, call/WhatsApp link, deactivate), customer profile (totals, last purchase, tier history, gifts, points, dues). `#/tiers` (owner): manage tiers (add / edit / reorder / retire), benefits per tier, auto-rules, gift rules, preview of the refresh (dry run) then apply. Existing dues page stays untouched.
   **POS (web/pos.js)**: after the customer mobile is typed and found, show the tier chip + perks text + "Apply <tier> <n>% discount" one-tap button (sets the percent discount field; honours the existing discount UI and rules), and a reminder chip when `gifts_due` is non-empty. Keep every existing POS test green (tests/web/pos2_test.js, pos_units_test.js).
