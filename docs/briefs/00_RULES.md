## SQL conventions (all enforced by past audits)
* Additive + idempotent (paste twice = no error): `create table if not exists`, `create or replace function`, `insert ... on conflict do nothing`, `drop policy if exists` before `create policy`, `alter table ... add column if not exists`. Never `drop table`, never hard delete; retire with a status/active flag; append-only history where it is a record (see `_append_only23` in phase23.sql).
* RLS enabled on EVERY new table; `revoke all on <table> from public, anon, authenticated; grant select ... to authenticated` + a select policy; ALL writes go through SECURITY DEFINER functions (`set search_path = public`) that check `public.is_active()`, `public.can_loc(loc)`, `public.is_owner()` / `public.has_grant('<code>'[, loc])`, validate every input (null, NaN, ranges `abs(x) <= 1e12`, lengths), reject past/future dates sensibly, use `public.lock_check(date)` for money documents, take `p_client uuid` idempotency keys for creates (`public._client_lock(p_client)` then look up by client_id). `revoke all on function ... from public, anon;` then `grant execute ... to authenticated` only for functions the browser calls; helpers are revoked from authenticated too.
* New grants: insert into public.grant_defs (grant_code, module, sort, label_bn, label_mix, label_en, window_type, emergency_rule) ... `where not exists`. New settings: public.rules rows (key, module, kind 'switch'|'number'|'text'|'choice', default_value, labels bn/mix/en, hints, sort) `on conflict (key) do nothing`; every new feature has an ON/OFF rule (`public.rule_on('key')`). Owner can change them in #/switchboard automatically.
* Audit: `create trigger audit_<t> after insert or update on <t> for each row execute function public.log_change('id')` (see phase23.sql). Never expose cost price / salary to users without the right: salary & pay figures = owner or grant `salary_view`; costs = owner or `public.rpt_cost_ok()`.
* Timezone Asia/Dhaka for "today". Money numeric (never float), round(…, 2).
* Existing helpers you can rely on: is_active, is_owner, can_loc(loc), can_do(form,'enter|approve|view'), has_grant(code[,loc]), rule_on/rule_num/rule_txt/rule_val, lock_check(date), log_change, no_hard_delete(), _client_lock, profiles(id, staff_id, full_name, status), user_roles, user_locations, locations(id, code, name_bn, name_en, kind, status), items, customers, sales, sale_payments, suppliers, purchase_bills, stock_ledger, entries (jsonb forms), audit_log.

## Web conventions
* One file per screen group, header comment explaining the job and the server functions used. Escape every dynamic string with `esc()`. Min tap size 40px; no horizontal page scroll at 360px width; every page uses `shell(title, html, true)` (back arrow is automatic); sheets via `openSheet()` already carry a close ✕. Use `data-ctl="off"` on `<details>` / groups you do not want collapsed by the control kit; prefer `<select>` for pick-one lists (the kit collapses them), `data-act` handlers via `Object.assign(H, {...})`. Call `if (B.loadStatic) await B.loadStatic();` at the start of a page view (loads locations/rules). Locations list: `B.liveLocs(B.ENV.locs)`; staff names: profiles. Errors: show friendly bilingual text for known server codes, raw message otherwise.
* Photos: reuse the existing photo helpers (grep `uploadPhoto` / `shrink` in web/stock2.js, `B.s2`), bucket `photos` is private (signed URLs).
* Fonts are small by design (12-13px) except where your brief says otherwise.
