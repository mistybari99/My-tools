Phase file: supabase/phase46.sql (+ phase46_test.sql). Web: web/notifications.js (+ tests/web/notifications_test.js). Ops files (you own): `.github/workflows/backup.yml`, `.github/workflows/notify.yml`, `tools/backup_dump.py`, `tools/notify_digest.py`, `tools/test_ops.py` (unittest against a fake local HTTP server), docs/OPS_SETUP.md. Regs: docs/regs/notifications.md. DB names a46*.
Read docs/briefs/00_RULES.md first.
Owner's words: "Auto Backup System - you can use GitHub / my Google Drive (ask if needed)", "Version saved on GitHub", "Notification - Gmail".
## Hard constraints
* The sandbox cannot reach supabase.co; the owner pastes SQL. Backups and email must run WITHOUT any person or this sandbox: use **GitHub Actions** (cron) in the owner's PRIVATE repo `mistybari99/My-tools`. Secrets are entered by the OWNER in GitHub (Settings -> Secrets); never ask for them, never write them anywhere; never use or document the Supabase service_role key. Use a dedicated, least-privilege Supabase Auth user (the "ops bot") instead.
* Backup data (contains sales, costs, salaries) must only go to the PRIVATE repo / the owner's own Drive. Never to the public repo `islamia-bos-app`. Put dumps on a separate orphan branch `backups` (never on the code branches) so code history stays small; keep `latest/` plus dated folders `YYYY/MM/DD/`; gzip ndjson per table + manifest.json (row counts, sha256, schema version) - "versions saved on GitHub" = every run is a commit. Prune is NOT automatic (history is the version store) but document how to.
## What to build
1. **SQL (phase46.sql)**:
   * `ops_accounts(user_id pk, purpose 'backup'|'notify', active, created_by, created_at)`: the owner marks the bot user (function `ops_account_set(p_user, p_purpose, p_active)` owner-only). Helper `_is_ops(p_purpose)`.
   * `backup_dump(p_table text, p_after_id text default null, p_limit int default 2000) returns jsonb` SECURITY DEFINER, only for an active ops account with purpose 'backup' (else 'not allowed'): returns `{rows:[...], next:<cursor or null>, total}` for a WHITELISTED set of public tables (generate the list from information_schema at call time excluding auth/storage schemas, excluding any table named like `%_secret%`, login/PIN data (login_failures, anything holding password/pin hashes - grep schema for such columns and exclude), and the new table `ops_*` internals; document the list), keyset pagination by primary key / ctid-free ordering, rows as jsonb (to_jsonb). Also `backup_manifest()` (tables, row counts, max updated_at, schema fingerprint = md5 of column list). `backup_log(p_status, p_detail jsonb)` lets the bot record runs in `backup_runs(id, started_at, finished_at, status ok|failed|partial, tables int, rows bigint, bytes bigint, detail jsonb, destination)`; owners can read `backup_runs`; alert when the last OK run is older than `backup_max_age_hours` (rule, default 36).
   * **Notifications**: `notifications(id, user_id null = all owners, audience owner|manager|all, kind, level info|warn|bad, title_bn/en, body_bn/en, route, key text unique-per-day idempotency (kind+key+day), created_at, read_at/read_by (per-user reads in `notification_reads(notification_id, user_id, read_at)`), emailed_at)`. `notify_scan()` (callable by ops 'notify' account and by the owner) generates notifications idempotently from existing data: red exceptions open > N hours, pending approvals older than N hours (needs_you_oldest logic of phase28), low stock count, expiring batches within N days, supplier dues overdue, customer credit limit breaches, shops with no day-close (14-1) by `day_close_deadline` rule, wastage spike, big cash short/over, parallel-month decisions waiting, backup stale/failed, unsent... (only what exists; guard optional tables with to_regclass). Rules for every kind: switch + threshold numbers (defaults sensible, all editable in Switchboard). `notifications_for_me(p_limit)`, `notification_read(p_id)`, `notification_read_all()`, `notifications_unread_count()` for the app. `daily_digest(p_date)` (ops 'notify' or owner) returns a jsonb summary for the email: sales today vs yesterday/last week (via sales_summary logic, net of returns), cash short/over, collections, dues totals, top 5 items, wastage, voids/discounts, open exceptions, pending approvals, stock alerts, day-close status per shop, attendance/payroll if tables exist, backup status; numbers only, bilingual labels. `urgent_alerts(p_since)` returns new bad-level notifications not yet emailed and marks nothing (the bot calls `notifications_mark_emailed(ids)`).
2. **Web** `web/notifications.js`: a bell with unread badge in the header is registered by the lead (document in regs how: `B.notifications.badge()`), page `#/notifications` (list newest first, filter unread / level, tap opens the route and marks read, mark all read, settings link to Switchboard). Poll the unread count every 60 s while the app is open (cheap RPC), no push.
3. **Ops scripts** (Python 3 standard library only, `urllib`, no pip installs except optional `rclone` binary step in the workflow):
   * `tools/backup_dump.py`: env SUPABASE_URL, SUPABASE_ANON_KEY, BOT_EMAIL, BOT_PASSWORD -> POST /auth/v1/token?grant_type=password -> for each table page through `rest/v1/rpc/backup_dump` -> write `out/<table>.ndjson.gz`, `manifest.json` (counts, sha256, started/finished, schema fingerprint compared with `backup_manifest()` row counts: mismatch = failure) -> call `backup_log`. Retries with backoff, exit non-zero on any failure, never prints secrets, redacts tokens in logs.
   * `tools/notify_digest.py`: login -> `notify_scan()` -> `urgent_alerts` and (at the configured hour) `daily_digest` -> build a plain, mobile-friendly HTML + text email in Bangla/English -> send via Gmail SMTP (`smtplib` SSL smtp.gmail.com:465, env GMAIL_USER, GMAIL_APP_PASSWORD (a Google "app password"), MAIL_TO list) -> `notifications_mark_emailed`. `--dry-run` prints the email and sends nothing.
   * Workflow `backup.yml`: schedule daily 02:30 Asia/Dhaka (cron in UTC) + workflow_dispatch; checkout the `backups` orphan branch (create it if missing), run the script, commit with message `backup YYYY-MM-DD HH:MM rows=N`, push; optional Google Drive step (rclone) that runs only if `GDRIVE_SERVICE_ACCOUNT_JSON` + `GDRIVE_FOLDER_ID` secrets exist (explain how the owner creates a Google service account + shares a Drive folder with it; or `rclone` OAuth remote token in a secret). `notify.yml`: schedule every 30 minutes for scan + urgent mail and a daily digest at 08:00 and 21:00 Asia/Dhaka. Concurrency groups, `permissions: contents: write` only where needed, pinned action versions (checkout v4).
   * IMPORTANT: scheduled workflows only run from the repository DEFAULT branch. State this clearly in docs/OPS_SETUP.md: the owner must merge/copy these workflow files to the default branch of My-tools (or tell the lead, who will do it when asked).
   * `tools/restore_backup.py`: restores from a backup folder into a database through a generated SQL file (`--dry-run` prints counts); documents the order, and that restoring is done by the owner in the Supabase SQL editor from the generated file (no direct DB access needed). Test it on the local Postgres.
4. **docs/OPS_SETUP.md** (Bangla + English, step by step for a phone user): create the bot user (Auth -> Users -> Add user email/password), run the SQL, mark it as ops bot (`select ops_account_set(...)` one-liner), add the GitHub secrets (exact names), create a Google app password for Gmail (2-step verification required) and optionally the Drive service account, run the workflows once manually, how to see backups, how to restore, how to rotate the bot password, what is NOT protected (e.g. Storage photos are not in the DB dump: document `tools/backup_photos.py` listing the `photos` bucket via the Storage API with the bot's JWT and copying files into the same backup branch only if size < limit, else Drive only; build it if feasible).
