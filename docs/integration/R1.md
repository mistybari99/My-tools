## 1. What it does

1. A staff member (linked to an employee record) sends a request: advance or salary (the due pay of an approved payroll run), amount, reason, needed-by date. A payroll manager can enter one for a colleague (`on_behalf`). Any staff with a place can send a supplier payment request (supplier, amount, which bill or due, date needed, optional supplier-side contact).
2. ONE responsible person decides: the owner (default), everyone with a role, or one named person, set in `pay_request_approver_set` (staff) and optionally a different one for supplier requests. The owner can always decide. Decision: approve (on the date asked, or another date, optionally a smaller amount), or reject with a reason. Approved requests can be re-dated until paid. The maker never decides or pays his own request; the only exception is the owner where the project already lets him approve his own entries (`owner_self_approve` on and not in named mode).
3. Staff see received / approved with pay date / a different date (flag `date_changed`) / rejected with reason / paid, with a timeline (`pay_request_events`). In-app notes go to `notifications` (phase 46), aimed at one person.
4. On the pay date (or later) the request shows in the Due list of the approver. Paying calls the EXISTING function (`staff_advance_add`, `payroll_pay`, `pay_supplier`) from `pay_request_pay`; the payment source is chosen at that moment (mode, or a money account of phase 87, sent as the `ma#id;` tag), so the journal is the one the old functions make (tested: Dr = Cr, account balances).
5. Policy `pay_requests_required` (verbal request policy, default OFF): advance and salary payments are refused (`pay_request_required`) unless an approved, due request backs them; same for supplier payments with `party_requests_required`. The old screens are accepted when a matching request exists (it is linked and marked paid). One exception with a reason: `pay_request_exception_open` (who may: setting `pay_request_exception_mode` reason / owner / never) logs a line of the new kind `r1_unbacked_payment` in the Exceptions list. The phase 87 one-off override (event `r1_pay_advance`, `r1_pay_salary`, `r1_pay_supplier`) also works.
6. Limits (blank = none): `pay_request_max_per_month`, `pay_request_advance_ceiling` (open advances + open advance requests + this one).

## 2. Settings (table `rules`, all defaults = today)

`pay_requests_on` off, `pay_requests_required` off, `pay_requests_required_kinds` both, `pay_request_approver_mode` owner (+ `_role`, `_user`), `pay_request_exception_mode` reason, `pay_request_max_per_month` blank, `pay_request_advance_ceiling` blank, `party_requests_on` off, `party_requests_required` off, `party_request_approver_mode` same (+ `_role`, `_user`). The six approver keys cannot be changed one by one from the browser (guard trigger, message `use pay_request_approver_set`).

## 4. Behaviour notes

- Payment of a request is one row (a request is paid in one go from the due list); the gate also accepts several direct rows that add up to the approved amount (split supplier payments). A smaller direct payment leaves the request approved with the rest still due.
- A supplier payment held by the W1-E limit (`supplier_pay_over`) cannot be completed from the due list when the payer is not the owner: `pay_request_pay` stops with `held_by_payment_limit` and nothing is written. The owner is never held.
- The payer needs the right the old function already demands (`payroll_manage` at the person's place for an advance, `_pr_ok` for payroll, `supplier_pay` grant for suppliers). Seeing the Due list needs only to be the approver or the owner; if the approver lacks the payment right the old function says `not allowed` and the owner pays.
- A salary request is paid from the oldest approved payroll line with an amount due; with none, `no_payroll_due`. More than due: `more_than_due` from `payroll_pay`.
- Rows are never deleted; a request is cancelled, rejected or paid. Every change has an event line and an `audit_log` line.
- Not built: reminders for requests waiting long (the existing notify scan is not hooked), SMS or WhatsApp notes, a salary request before the payroll run is approved (use an advance), a report of requests per month.
