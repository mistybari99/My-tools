# Integration note I-1: Wave 1 integration (phase99) and the web wiring

Package I-1 (integrator) of `docs/UNIFIED_BUILD_PLAN.md` section 4.3. SQL number: **phase99** only, pasted LAST (after phases 88 to 98, which may be pasted in numeric order). Paste-twice safe. Files: `supabase/phase99.sql`, `supabase/phase99_test.sql`, `tests/sql/phase99_before_after.sh` (+ `p99_fixture_extra.sql`, `p99_snap_extra.sql`), `tests/sql/ORDER.txt`, `tests/sql/run_all_sql.sh`.

## 1. What phase99 does

1. **Guard**: stops with `phase99 needs these phases pasted first (in this order, each once): ...` and the names of the missing phases.
2. **`_i1_apply_hooks()`**: ONE function that applies every exact-text hook the seven packages shipped, in a fixed order, with the helper each package shipped, and returns one entry per patch (`true` = patched now, `false` = already there). Order: A (`_w1a_patch`, marker bos88: `_cust_bal`, `customer_dues`, `customer_ledger`, `opening_balance_post`), B (`_w1b_patch`, bos89: `lock_check`, `_acct_locked`, `record_sale2`, `cash_move_add`, `quick_expense_add`, `save_purchase`, `production_post`), C (`_w1c_patch`, bos90 `employee_status_set`, bos91 `sale_return`, `void_sale_return`), D (`_w1d_patch`, bos92 `_p27_pl`, `partner_calculate`, `c_partner_month_split`; bos93 `_p27_pl`, `report_run2_core`, `_r3q_e3_weak_control`, `_r3q_e2_expense_trend`, `brand_pnl`; then `_w1d_hooks_apply()` for `_daybook_lines` and `_acct_docs`), E (`_m_patch`, `pay_supplier` w1e94, `cash_move_add` w1e94c, `acct_journal_post` w1e95), F (`_w1f_patch`: bos96 `_acct_docs`, `_daybook_lines`, `_e_balance_check`, `acct_cash_flow`, `daybook_vs_journal`; bos97 `_acct_docs`, `_daybook_lines`, `collect_payment`, `record_sale2`), C's optional scan hook (bos90 `notify_scan`, inert until `exit_alert_hours` is set). The patch texts are the ones in the integration notes W1-A to W1-F, copied by a script from the package files, not retyped.
   * A missing patch site stops the call with `patch site not found in <function>: <text>`. The whole call is one statement: nothing is half patched (tested: an early hook is rolled back when a late one fails).
   * After the patches `_i1_hooks_state()` must show all 37 expected (function, marker) pairs (`_i1_expect()`); a helper that skipped a function silently (phase87 `_m_patch` returns false when the function already carries bos87) is caught here and stops the call.
   * The patches do not overlap (each package edits its own anchor text), so the order does not change the result; it is fixed so that the result is the same after a fresh paste and after a re-patch.
3. **`_i1_exc_kinds()` and `_i1_exc_kinds_apply()`**: the Exceptions list (`money_exceptions`) has ONE list of 18 kinds (phase87: 7, phase89: 3, phase94: 8) and ONE function that writes `money_exceptions_kind_check`. It reads the live constraint in both shapes (`ARRAY['a'::text,...]` and `'{a,b}'::text[]`), adds the known kinds, keeps any kind it finds, writes the sorted list back, and does nothing when the list is already right.
4. All helpers are closed to browsers (`revoke ... from public, anon, authenticated`). To put the hooks back after an older phase was pasted again: `select public._i1_apply_hooks();` (or paste phase99 again).

## 2. Fixes made in two unpasted phase files (they were found by building 88 to 98 together)

* `supabase/phase94.sql` `_w1e_add_exc_kinds`: it read only the `ARRAY['a'::text]` shape and failed with `cannot determine type of empty array` when phase89 had already written the `'{...}'::text[]` shape. It now reads both shapes (and raises a clear message for an unknown shape). Without this fix phases 94 and 95 could not be pasted after 89.
* `supabase/phase90.sql` `_w1c_employee_status_set`: with the hook installed the exit step already ran inside `employee_status_set`, so the wrapper answered `exit: {skipped: done}`. It now reports what the step logged in the same transaction. The web does not call the wrapper (`employees.js` calls `employee_status_set`, which carries the hook).

## 4. Web wiring (all registered once)

* `web/ia.js`: `openparties`, `periodlock`, `moneycontrols`, `otherincome`, `freshness` (group acc), `profitcheck` (reports), `returnrules` (settings), `bankreceipt` (cust). No Home tile, no bottom bar slot, no `mod`, so no home slot is taken. `ia_test` passes.
* `web/index.html`: the seven script tags after `moneyaccounts.js`. `web/sw.js` has no precache list (network first, cache as fallback), so nothing was added there.
* `web/pos.js`: `{parked:true, held_id}` from `record_sale2` is a sent sale ("Held for the owner", no receipt, no retry).
* `web/salereturn.js`: the return picker (`BOS.returnRules.preview` / `pickerHTML` / `collect`) draws under the quantities when the server has phase 91; the save calls `_w1c_sale_return` with the restock lines, receipt number and override reason; without phase 91 or without `returnrules.js` the old form and `sale_return` are used. Return rule codes are shown in words.
* `web/pay.js`: bank transfer and cheque rows (mode `bank`, `cheque_no`, `cheque_date`, `exception_reason`) only on payment states flagged `receipt` (POS: `pos_split_payment`, dues: `customer_collection`) and only while `receipt_bank_on` is ON (read once from `_w1f_receipt_settings`). With the switch OFF the screen is the old one. `web/dues.js` shows "Opening due" for the first ledger row.
* `web/forms_stock.js` and `web/paths.js`: the `confirmSwitch` lines of W1-G. `web/nav.js` (Home) and `web/accounts.js`: `BOS.freshness.mount` strip (only for people with Accounts view; silent without phase 98).
* "Waiting for the approver" for `pending` answers in `web/cashmoves.js`, `web/purchase.js`, `web/accounts.js`.
* `tools/notify_digest.py`: the scheduled posting call after the scan. `.github/workflows/backup.yml`: the four patches of W1-G; `backup_encrypt_on` stays OFF, so nothing changes until the owner supplies the secret and switches it on.
