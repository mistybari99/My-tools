# Integration note R2: announcements, to-do list, shift schedule (phases 130, 131, 132)

Owner request R2 (three features, every one a setting that is OFF by default). SQL numbers: **phase130** (announcements), **phase131** (to-do list), **phase132** (shift schedule); range 130-139 was free. Each is paste-twice safe. 130 and 131 need only the rules / grants engine (phases 7, 8, 11) and `_client_lock` (phase 10); 132 also needs phases 41 and 42 (employees, shifts, shift pattern, attendance helpers). They do not need each other. Paste them after phase99 (or any time after their own needs).

No live database was touched. Everything ran on a local throwaway Postgres 16 (port 5600), fresh build through phase 99, then 130 to 132.

## 1. What each phase adds (all new names start `r2_` / `_r2`)

| | Setting (rules, module `people`, OFF) | Grant (who) | Tables | API |
|---|---|---|---|---|
| 130 | `announce_on` | `announce_post` | `r2_announcements`, `r2_announce_seen` | `r2_announce_state / _post / _active / _seen / _mine / _receipts / _withdraw` |
| 131 | `todo_on`, `todo_repeat_on` | `todo_assign` | `r2_todos` | `r2_todo_state / _assign / _mine / _given / _set / _manage` |
| 132 | `shift_on` (OFF), `shift_mates_on` (ON, matters only with `shift_on`) | `shift_manage` | `r2_roster_days` | `r2_shift_state / _my / _roster / _template_save / _report`, `r2_roster_set / _clear / _week / _copy_week` |

* **Who may post / assign / schedule is the existing grant system**, not a new one: the owner gives `announce_post`, `todo_assign`, `shift_manage` to a role (Rules page, role grants) or to one person (Delegation board, optionally for one place only). `grant_defs` rows are seeded; no role and no person holds them by default, so only the owner can act until he delegates. A person's grant limited to one place lets him post only to that place (announcements) or schedule only the people whose main place it is (shifts).
* Every table has row level security and **no browser write**; every write is a `security definer` function that checks the switch, the grant and the input. Nothing is deleted (a `no_hard_delete` trigger; withdrawn / cancelled / cleared rows stay with who, when and why). Every row change is an `audit_log` line (`log_change` trigger). Read receipts are append-only (update and delete refused by a trigger).
* Helper functions are closed to browsers (`revoke ... from public, anon, authenticated`), except `_r2_ann_to_me`, which the read policy needs (it only answers about the caller).

### 1.1 Announcements (phase 130)
* Post: title (1-120), text (0-2000), urgent flag, audience `all | role | location | person`, start (default now) and expiry (blank = until withdrawn). A client id makes a retry harmless.
* Audience: `all` = every active login; `role` = holders of the role; `location` = people linked to the place in `user_locations`; `person` = one login. **Known limit:** a manager who reaches every place only through the `management` role and has no `user_locations` row for a place is not counted in that place's audience.
* A person reads only what is addressed to him and live (table policy and `r2_announce_active`); the poster reads what he posted; the owner reads all. Seen = one row per person and message, written only by `r2_announce_seen` and only for a person it is addressed to while it is live. The poster and owner see "read / not read yet" lists (`r2_announce_receipts`).

### 1.2 To-do list (phase 131)
* Task: title, detail, due date (today or later), priority `low | normal | high | urgent`, status `open | done | cannot | cancelled`, the note (done-note optional; `cannot` and `cancel` need a reason), who and when for every move.
* A task given to a **role** becomes one row per active holder at that moment (people who join the role later do not get it). Person tasks are one row.
* The assignee sees only his own (table policy and `r2_todo_mine`); the giver sees what he gave (`r2_todo_given`); the owner sees all. The assignee moves his task `open -> done | cannot`; the giver or owner may `cancel` (reason) or `reopen`.
* Repeat (`todo_repeat_on`, OFF): with it ON, marking a repeating task done or cannot creates the next one for the same person, due = the later of (its due date, today) + 1 day (daily) or + 7 days (weekly); one open child at a time. With it OFF a repeat other than "none" is refused (`repeat_off`).
* Overdue = open and due date before today (Dhaka).

### 1.3 Shift schedule (phase 132)
* **Reuses** existing tables: shift templates = `shifts` (name, start, end, place); the recurring weekly pattern = `employee_shift_assignments` (READ only, written by the existing `shift_assign`); holidays and approved leave (`holidays`, `leave_requests`) are READ to mark a day. `shift_save`, `shift_assign`, `_att_*` and every attendance / payroll function are untouched.
* New: `r2_roster_days` (one active row per person and day that says a shift or an off-day, plus a leave / swap note and the place). A day with no row follows the weekly pattern, else shows nothing (nothing is invented).
* Staff: `r2_shift_my(from, days)`: shift, off, note, holiday, approved leave and, with `shift_mates_on`, who else is on at the same place that day (names and times only).
* Schedulers (`shift_manage`, scope = the person's primary place, same rule as `attendance_manage`): roster grid by place, set / clear a day, set a whole week, copy a week (existing cells are kept), add / edit / retire a template (a non-owner only at his own place; the owner may use "every place").
* Soft link: `r2_shift_report(loc, from, to)` compares the roster with `attendance_days` (present, late, half day, leave, absent, no record, worked on an off-day). It runs only when the table exists (otherwise `attendance:false`), reads only, and is readable by `shift_manage` or `attendance_manage` holders of the place.
